# M7.6 — The sandbox: spawner, trainer and inspector: specification

Milestone M7.6 of `docs/gcity-design.md` §16, **proposed as a new milestone** between
human scale (M7.5) and look and feel (M8). Written before implementation (standards §2.1,
§10.2). Status: **proposed** (Claude Code, 2026-10-02), from CEOGG's request the same
day: "we need to build a native trainer and spawner for testing, maybe something like
Garry's Mod", with these answers: a new M7.6 after M7.5; spawn menu, trainer toggles, AI
and time controls and inspect overlays; dev builds only.

**Why this milestone exists.** Today a situation can only be set up by writing code: a
fixture generator, a test, `tools/make_sites.gd`. CEOGG cannot put two armed guards
behind a wall on the Deck and watch what they see. Every later milestone is tuned by
playing (M8's feel, M9's raids), so the game needs a place where anything the content
defines can be spawned, any rule can be watched, and any session can be kept as a test.

**Preconditions.** G7.5 is signed: the sandbox builds on the creator tool's lot, cursor
and palette (M7.5 claims 14–16) and on the human-scale rules. This spec is approved,
with its decisions.

**The claim of the milestone.** `--sandbox` opens a lot where, from the controller alone,
anything in the content can be spawned at the cursor, the player can be made unkillable,
supplied, moved and lifted, the AI and the clock can be held, slowed and stepped, and what
the sim knows (sight, awareness, paths, support, volumes) is drawn over the world.
Everything acts through `SimRoot.submit`, so the sim still decides, and a session can be
saved as a replay fixture that reproduces. None of it is in a release export.

**What this milestone is not.** Not a shipped game mode (decision 1). Not physics props:
the sim has no rigid bodies, so there is no physics gun; what is spawned obeys the same
rules as anything else. Not a console: nothing typed and nothing executed (CLAUDE.md §10:
no keyboard tools, no untrusted script). Not noclip: walking through walls would break
M7.5's body invariant, which this milestone keeps (decision 3 gives fly and teleport
instead). No new content kinds.

## Decisions this spec takes

Approved with the spec, or changed by CEOGG before it is.

1. **Dev builds only, by folder.** Everything for the sandbox lives in `sim/sandbox/`,
   `client/sandbox/` and `sandbox_content/`, and the release export preset excludes all
   three. The shipped game has no sandbox code to reach. A test reads
   `export_presets.cfg` and fails if any of the three is not excluded.
2. **The sandbox sim is assembled beside the game's, not inside it.** `SimAssembly.build`
   does not change. `SandboxAssembly.build` (in `sim/sandbox/`) calls it, loads the
   `sandbox_content/` entries into the content database first, and attaches
   `SandboxSystem` last, always last, so the order is still fixed. A fixture records which
   assembly made it, and `tools/replay_hash.gd` uses the same one. The game's own fixtures
   and their hashes do not move: their assembly has no sandbox system and their content
   digest has no sandbox entries. Rejected: always registering the sandbox and refusing
   its commands outside the mode, because that ships the code (decision 1).
3. **Trainer effects are generic rules at their neutral value, not special cases.**
   Each effect is a stat read by the system that owns the rule, through the stat
   resolver, with a base value that changes nothing. The sandbox only adds modifiers:
   - `damage_taken` (ActorSystem, per mille, base 1 000): god mode sets it to 0.
   - `rounds_per_shot` (CombatSystem, base 1): infinite ammo sets it to 0, so a shot is
     resolved but no round leaves the magazine.
   - `gravity` (MovementSystem, base 1): fly sets it to 0. The actor does not fall, and
     the dy level change works without stairs. The body rule still holds: a flying body
     is never inside anything.

   These are real rules a later perk, armour or jetpack can use too, which is why they are
   not sandbox flags. A stat that is not yet read is not added (CLAUDE.md §2). Teleport and
   set-health are `SandboxSystem` commands that call public methods the owning systems
   already have, or gain, with the same validation as any other caller.
4. **Time is the client's.** Pause and resume are the existing `sim.pause` and
   `sim.resume`. Single step, slow motion (½, ¼) and fast forward (×2, ×4, within the
   frame budget) change how many ticks the client steps per frame. The sim's tick is
   untouched, so every rule and fixture means what it did.
5. **The spawn menu is a device app, lists come from content.** A `sandbox` app (an app
   definition in `sandbox_content/`, registered only in the mode) lists every agent
   profile, kit, item template, build piece and site the content database holds, by kind.
   Nothing is listed by hand, so a new weapon file appears in the menu with no code (the
   extension test, Q4).

## Claims

### The mode (`client/sandbox/`, `sim/sandbox/`)

1. **`--sandbox` opens the lot.** The creator tool's flat, owned lot with the player and
   the device, assembled by `SandboxAssembly`. The run log records every sandbox command.
   Release export: the three folders are excluded (decision 1, with its test). The game's
   assembly registers no `sandbox.*` command (test).

### Spawner

2. **Spawn anything at the cursor.** From the sandbox app: a guard (any agent profile,
   any kit, facing the camera), an item into the player's inventory (weapons, magazines
   filled or empty, ammunition, parts; the sim has no items lying loose on the ground,
   and this milestone adds none), a build piece (as the creator
   tool places it), a whole site raised at the cursor. Each goes through an existing
   command (`agent.spawn`, `item.spawn`, `build.place`, `site.raise`), so rights, support
   and the body rule judge it.
3. **Remove and reset.** `sandbox.despawn` removes the actor or piece under the cursor
   (an actor's kit is dropped the way M7 claim 12 drops it, conserved).
   `sandbox.clear` returns the lot to empty. Both are refused for the player.

### Trainer

4. **God mode, infinite ammo, fly** (decision 3), each a toggle in the app sent as
   `sandbox.trainer {actor, effect, on}`. Each is proven: with god mode a full magazine
   emptied into the player leaves its health unchanged; with infinite ammo a
   hundred-round burst leaves the magazine full and the shots resolved; flying, a step
   off a roof does not fall and the body property (M7.5 claim 2) still holds.
5. **Teleport and health.** `sandbox.teleport {actor, cell}` to any cell where the body
   fits (refused otherwise, with the reason); `sandbox.set_health {actor, node, value}`
   within the node's range; a revive for a dead actor through `actor.respawn`.

### AI and time

6. **Hold the AI.** `sandbox.ai {agent | all, frozen | blind | deaf, on}`. A frozen agent
   neither perceives nor acts; a blind one hears; a deaf one sees. Each is a perception
   or agent rule at its neutral value (decision 3's form), so no fixture moves. A
   metamorphic test: a blind guard's awareness of a player in plain sight never rises,
   and a deaf guard ignores the gunshot it would otherwise investigate.
7. **Hold the clock** (decision 4): pause, step one tick, ½, ¼, ×2, ×4, shown on screen.
   A test: N single steps produce the same state hash as N ticks run straight.

### Inspector (client only)

8. **See what the sim knows.** Toggleable overlays: sight lines and their eye and centre
   points, each guard's awareness and alert state, last-known positions, current paths,
   portal volumes and their breach costs, support depth per piece, body cells, parcel
   bounds and owners. They read sim queries and write nothing: a test toggles every
   overlay over a running fixture and the state hash at every tick is unchanged.

### Recording

9. **A session is a fixture.** The app saves the session's seed, assembly and input log
   as a replay fixture in `user://fixtures/<date-time>.json`, in the existing fixture
   schema. `tools/import_fixture.py` validates it and copies it into `tests/replay/`,
   where `tools/test.sh replay` checks it like any other. Property: 1 000 random sandbox
   sessions (spawns, trainer toggles, AI holds, steps), each saved, reproduce their hash
   twice.

### Verification

10. **Every sandbox command is an untrusted boundary**: exact payloads, ranges, actor and
    cell validity, with a fuzz corpus in the repo (standards §5).
11. **The game did not move.** Every G7.5 replay fixture reproduces its hash unchanged.
    The decision-3 rules at their base values, and the sandbox outside the game's
    assembly, are what make that true.
12. **Mutation score ≥ 75 %** on the new and changed `sim/` files, both passes reported.
13. **Deck run.** On the Deck, from the controller only, CEOGG sets up: two guards with
    rifles behind a wall, the player in god mode, sight lines on, then saves the session
    as a fixture. The time it took and CEOGG's notes are recorded. 40 fps (1 % low) with
    the overlays off; the cost with them on is recorded, not held to the budget.

## Order

1 and decision 2's assembly first (everything runs in it), then 2–3, 4–5 (one owning
system per session: actors, combat, movement), 6 (perception and agents), 7, 8, 9, then
10–13 to close the gate.

## Out of scope

Physics props and a physics gun (no rigid bodies in the sim). Noclip (decision 3).
Scripted scenarios or a console. A sandbox in the shipped game. Saving a sandbox lot as a
playable save (it is a fixture or a site, never a save). Network play in the sandbox.

## Consequences for M8 (amendment proposed with this spec)

M8's gate says the sim did not move "since G7.5". M7.6 adds `sim/` code, so M8's
baseline becomes **G7.6**: in `docs/specs/M8-look-and-feel.md` (preconditions, claim 13)
and the G8 row of standards §11, "G7.5" becomes "G7.6". The fixture set is the same,
because M7.6 moves no fixture hash (claim 11). M8 claim 12's "debug overlay behind a flag"
may reuse claim 8's overlays; nothing here requires it.
