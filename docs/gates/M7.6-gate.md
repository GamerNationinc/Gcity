## 4. Debt and deviation log

| # | Item | Kind | Scheduled |
|---|---|---|---|
| 1 | **`SandboxAssembly` does not read `sandbox_content/` itself** (decision 2 says it loads the entries first). The sim may not touch files (CLAUDE.md §5; `ContentLoader` lives in `client/`), so `client/sandbox/sandbox_mode.gd` loads the game's content and then the sandbox's into one database and hands `SandboxAssembly.build` to the host (`LocalHost.use_assembly`). The order decision 2 cares about holds: content first, then the game's systems, then `SandboxSystem` last (tested). | deviation from the spec's wording | closed |
| 2 | **The world view reaches the sandbox by path, not by name.** A `class_name` from an excluded folder would not parse in a release export, so `client/world_view.gd` loads `client/sandbox/sandbox_mode.gd` with `load()` when `--sandbox` is given, and a build without it says so in the HUD and the run log and opens the creator's lot. Checked on the release export: `--sandbox` notes "this build has no sandbox (release export)", no errors; the binary carries no compiled sandbox script (no `.gdc` remap for any sandbox file; the script class and UID caches still name the paths, as metadata). | implementation note, decision 1 | closed |
| 3 | **`sandbox.clear` leaves bodies.** The spec says it "returns the lot to empty"; the dead are traces other systems count (corpses, the run score) and no rule removes them, so clear removes every other living actor and every piece the player may remove. | deviation, claim 3 | open: CEOGG, keep or add a body removal |
| 4 | **An agent and its kit are one sandbox command** (`sandbox.spawn_agent`), not `agent.spawn` followed by item commands. Ids are allocated as commands run, so a client cannot name the guard it just spawned in the same tick; a site raising its guards meets the same problem and arms them with `ItemSystem.arm` (its comment says why). The sandbox command calls the same public methods `agent.spawn` and a site's kit use (`PerceptionSystem.spawn`, `ItemSystem.arm`, `ActorSystem.wield`), checks the body fits first, and is whole or refused. | deviation from claim 2's wording | closed |
| 5 | **Build pieces are not on the Spawn app.** The creator's controls (A places the palette's piece at the cursor, Y the next piece) already place every build piece through `build.place`, as claim 2 asks ("as the creator tool places it"); the sandbox keeps them. | implementation note, claim 2 | closed |
| 6 | **`site.raise` gained a third form, `{actor, site, at}`** (`sim/world/site_system.gd`): the site's base in that cell, its pieces, guards and terminals under the raiser's rights there, its lots left where they are. The two older forms are unchanged, so every fixture replays. A site stands once per sim: raising one again needs a restart (`sandbox.clear` takes its pieces down but the site system still counts it raised); the app says so instead of sending it. | change to a game command, claim 2 | open: `sandbox.clear` un-raising sites, if CEOGG wants it |
| 7 | **Magazines are spawned empty**, and ammunition by the 15; a full magazine is the inventory app's load (M5), which the sandbox player has. Agents spawn with full magazines (their kit). | implementation note, claim 2 | closed |
| 8 | **The three trainer stats live in `sandbox_content/stat/`, and an unregistered stat is its neutral value.** Decision 3 has each effect be a stat the owning system reads at a base that changes nothing; but the resolver's registered stats are part of its snapshot, so a new stat in `content/` would move every fixture's hash, and claim 11 says none moves. So `damage_taken` (ActorSystem, per mille, base 1 000), `rounds_per_shot` (CombatSystem, base 1) and `gravity` (MovementSystem, base 1) are read where registered and taken as their base where not; the sandbox's content registers them. A later armour, perk or jetpack makes one real by moving its file into `content/` (and moving every hash once, then). Tested both ways (`test_the_game_registers_none_of_the_trainer_stats`); every game fixture reproduces. | deviation, decision 3 | closed |
| 9 | **Fly is on the triggers** (right lifts a level, left drops one, a level every 8 ticks while held), the only Deck buttons free in the sandbox. M7.7 (approved) puts sprint on the left trigger; when it lands, the sandbox keeps the triggers for flying (a flying body does not sprint) or moves fly, and M7.7's button test decides. Pressing a trigger with fly off says so on the HUD. | implementation note, claim 4 | open: M7.7 |
| 10 | **`ActorSystem.set_health` is new**, the public method `sandbox.set_health` calls (decision 3: "public methods the owning systems already have, or gain"): a living actor's node from 0 to its most; a fatal node set to 0 kills as damage would. The revive is the game's `actor.respawn`, which needs the body (the death screen already offers it). | change to a game system, claim 5 | closed |
